Critical Flaw in MCP Server SDK Leaked Client Responses via Shared Request IDs

dev.to · Wed, 21 Oct 2026 11:11:06 +0000

A security flaw in the Model Context Protocol TypeScript SDK allowed HTTP servers to deliver responses to the wrong clients due to collisions in shared JSON-RPC identifiers.

A significant security vulnerability in the Model Context Protocol (MCP) TypeScript server SDK, tracked as GHSA-jm63-cq47-j5jp, has revealed a serious flaw that allowed HTTP servers to cross-deliver responses between unrelated users. The bug affected @modelcontextprotocol/server versions 2.0.0 through 2.2.0. Because the SDK matched inbound responses to active connections relying solely on the JSON-RPC request identifier—a sequential counter starting at zero for every client—concurrent requests from separate users shared identical identifiers, causing tool outputs and notifications intended for one client to be delivered to another.

The root of the issue stemmed from how the framework's official documentation structured server implementations. Example templates across popular Node.js frameworks, including Express, Hono, and Fastify, instructed developers to instantiate a single server and transport instance at application startup and share it across all subsequent HTTP requests. Consequently, what appeared to be a stateless transport inadvertently held in-flight request tracking across connections. Because the protocol-level identifier lacked an enclosing server-managed connection scope, concurrent traffic predictably resulted in race conditions that exposed sensitive data without requiring malicious exploitation.

Maintainers have resolved the flaw in version 2.3.0 by strictly preventing instance sharing, automatically rejecting duplicate connections and secondary requests on stateless transports. Developers using affected versions are urged to upgrade immediately and restructure their application architecture. Proper deployment patterns now require creating fresh server and transport instances per request or isolating them per session using dedicated session generators. Teams running multi-user HTTP deployments must also audit past interactions to determine whether sensitive tool results were leaked across tenants during high-concurrency periods.
