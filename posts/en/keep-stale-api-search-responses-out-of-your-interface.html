A search interface can show the wrong result even when every API request succeeds. Someone types a short query, immediately replaces it, and the older response arrives last. If every completed request updates the same result list, the older query wins. This practical example uses cancellation to reduce unnecessary work and a request version to decide which response still belongs to the interface. The examples are hypothetical. Cancellation and ownership solve different problems An AbortController lets a fetch consumer cancel work through an AbortSignal. That is useful, but the UI should still know which request owns the current view. A wrapper, cached promise or test double might finish despite cancellation. A version check makes the rendering rule explicit: only the most recent search may change results, errors or loading state. Test the order you hope never happens A useful test double lets you resolve promises in a chosen order. Start request A, then B; resolve B first and A second. The final rows should still belong to B. Also test these cases: Resolve A while B is pending. The loading indicator must remain on for B. Reject A after B succeeds. A's error must not replace B's successful view. Clear the query while A is pending. The list stays empty when A later resolves. Reject the current request. Show a useful failure message and clear its loading state. It does not cancel a server-side business transaction, guarantee that a remote operation was undone or replace authorization.
