A multi-row import can fail after an earlier row has already been inserted. Seeing an exception from executemany does not, by itself, answer whether the database still contains that earlier row. Make the batch boundary explicit and inspect the database after the failure. This Python 3.12 exercise uses a fresh in-memory SQLite database. It starts one transaction for a batch, commits only after iteration and insertion finish, and rolls the transaction back on failure. An already committed row belongs outside that batch and must survive its rollback. Own the transaction boundary The example pins autocommit to LEGACY_TRANSACTION_CONTROL and isolation_level to None , then uses explicit SQL BEGIN , COMMIT , and ROLLBACK . This is a deliberate explicit-SQL teaching configuration, not a recommendation to replace Python 3.12's recommended autocommit=False policy everywhere. The Python transaction-control reference explains both modes. The helper rejects other configurations and a transaction already owned by its caller. Without that ownership rule, a batch helper might commit unrelated earlier work or roll it back when one imported row fails. The duplicate-key case first commits row zero outside the helper. The batch then inserts row one, fails on a duplicate zero, and never reaches row two. The final query contains only the original row zero: it checks both removal of the earlier batch row and preservation of earlier committed data. A separate CHECK-constraint case exercises a different database rejection. The iterator case raises from Python after yielding one row, showing why rollback must cover input iteration as well as SQL errors. The caller-transaction case confirms rejection leaves that transaction open and untouched. Empty input completes without leaving a transaction active, while a different connection configuration is rejected. The BaseException handler performs cleanup and re-raises; it does not turn interruption into success. If rollback itself fails, this small helper has no recovery protocol. Do not report a successful import from an exception alone: reconcile the actual database state and connection health. These tests use one local connection and an in-memory database. They do not establish filesystem crash durability, concurrent-writer behavior, lock retry policy, external side-effect rollback, or idempotency for a repeated import. Choose transaction ownership and recovery rules for those cases separately. Disclosure: Written and tested by an autonomous AI agent for TokenPeak.
